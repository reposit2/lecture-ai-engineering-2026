## 宿題

- 取り組んだレベル：基礎

- やったこと（変更したファイル・設定・処理、または設計した取得方法）：app/config.pyのRAG_TOP_Kを5から2に変更した。これは通常のベクトル検索で返すページ数の上限を減らす変更であり、検索DBの再構築は行っていない。変更の目的は、今回の質問では上位2ページに必要な根拠が含まれているため、検索件数を減らしても正確に回答でき、入力トークン数と推定APIコストを削減できるかを確認することである。

- 比較した質問と、固定した条件（モデル・対象資料など）：質問：「第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？」モデルはgemini-3.5-flash-lite、対象資料は第1〜3回の本講義214ページとし、変更前後とも--trace付きで実行した。変更した設定はRAG_TOP_Kのみである。ただし、モデルが生成した検索語は変更前後で完全には一致しなかった。

- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：

|---|---|---|

| 回答の正確性 | 正確 | 正確 |
| 引用ページ | 第2回 p.51、52 | 第2回 p.52 |
| ツール呼び出し | `search_materials` 1回 | `search_materials` 1回 |
| 検索語 | `LoRA QLoRA 固定 学習` | `LoRA QLoRA 固定 学習 第2回` |

入力トークン数は約49.4%、推定生成APIコストは約17.1%減少した。一方、実行時間は5.04秒から11.18秒に増加した。

変更後の検索単独実行では、p.52とp.51の2ページが取得された。エージェントの回答では、p.52を根拠としてLoRAとQLoRAの違いを正しく説明できた。

変更後の初回実行ではGemini APIの503エラーが発生したが、再実行では成功した。`uv run pytest -q`では17件すべてのテストが成功した。

- 改善した例と、残る失敗・制約：

今回の質問では、Top-K=2でも必要な根拠が得られ、回答の正確性を維持しながら入力トークン数と推定APIコストを削減できた。

一方、応答時間は短縮されなかった。また、根拠が複数のページに分散する質問では、Top-Kを小さくすると必要な情報を取得できなくなる可能性がある。

変更前後でモデルが生成した検索語が異なり、実行も各1回であるため、今回の差をすべてTop-Kの変更による効果と断定することはできない。

- 気づき・疑問：

検索結果を多く取得すれば必ず回答が改善するわけではなく、必要な根拠が上位に含まれている場合には、検索件数を減らすことで効率を改善できると分かった。

今後は、複数ページの情報を組み合わせる質問でTop-K=2とTop-K=5を比較し、回答品質とトークン使用量のバランスを検証したい。
